Smart Factory Edge Platform

A plant-wide system that inspects every unit, warns before machines degrade and learns from every QA decision. Each production line runs on its own edge node and keeps working when the plant network or cloud is down. Rules judge numbers, AI models read images, signals and text, and people decide whatever the models are unsure of.

1Goals and scope

The platform grows the Line 3 quality-inspection demo into a plant-wide system built on one shared backbone, with four capabilities: edge data collection, vision defect detection, predictive maintenance and a feedback loop.

GoalProposed targetToday, Line 3 demo
Every unit has a disposition and a stored reason100% of units✓ Met in the demo
Units released without a person≥ 90%, zero escaped defects from auto-release96% in a simulated run
Drift caught before bad partsLine stop ≥ 1 unit before the first out-of-tolerance part3 units early, tool-wear scenario
Line keeps inspecting through an outage24 h without plant hub or cloudGateway store-and-forward only
Predictive maintenance lead timeOpen: needs failure historyNot built

Targets are proposals for the team to confirm. Demo figures come from the simulator, not a real line.

In scope

Line 3 (five stations) first, then every line in the plant, then further plants on the same images and config model.

Non-goals

AI never writes to a PLC or controls a machine. Safety functions stay in safety-rated PLCs. The platform does not replace the MES or ERP. No generated text makes a disposition.

2Design principles

Six rules decide every trade-off in this document. When one conflicts with throughput, the rule wins: a held part costs minutes, an escaped defect costs a recall.

PrincipleWhat it means in practice
Deterministic where it mattersTolerances, reaction plans, SPC and alarm codes are rules, versioned like code. A model can hold a part; it can never release a part the rules failed.
Each model reads what it is good atLaya reads text people write. Vision models read images. Signal models read vibration and load. None of them judges a measurement against a tolerance.
Calibrated gates, not raw scoresA model acts alone only above a confidence threshold set from measured error rates on this plant's data. Below it, a person decides.
Edge firstEverything a line needs to inspect runs on its edge node. The plant hub and cloud improve the system; neither is required to inspect a unit.
Every decision is reconstructableEach disposition stores its raw inputs, model versions, answers, rule results and policy trace.
People close the loopEvery held unit is reviewed by a named person, and those reviews are the labels that measure and retune the models.

4Layered architecture

Three layers sit under the business capabilities they serve: application, data and technology. Each depends only on the one below, so a database, broker or model runtime can be swapped without redesigning the applications.

6Edge node design

About ten small containers per line. Each model runs in its own service, so a crash, update or memory spike in one model cannot stop inspection.

Failure at the edgeWhat happens
Plant hub unreachableInspection continues. Results queue in the bridge and store; line-ui shows holds so a line lead can review on the spot.
A model service downUnits that need it are held; units that don't, such as records without a note, flow as normal.
Edge node downPLCs run the line on their own logic. Collectors resend their buffers; any gap is flagged and those units are held.

7.1 Language: what the Laya measurements showed

Three findings from the demo shaped how Laya is used everywhere in the platform. The charts below are the measurements behind them.

Integration rules for every Laya use

Give Laya the human text alone. With rule output mixed in (“Leak rate 0.61 ml/min, within tolerance”), it answered leak for healthy parts and missed an operator's dent report.

Use choice questions. Yes/no questions fail on the multilingual checkpoint (Figure 6).

Set TORCHINDUCTOR_COMPILE_THREADS=1. With torch 2.2, each checkpoint load forked 12 compile workers that kept a server's port bound after it exited.

Measure a question on new messages before building on it. In planning, Laya could not tell a confirmed report from a possible one, or read urgency or how critical an order is to the customer; a short word list in three languages could. Asking the same thing twice in different wordings and requiring agreement removed confident errors on the inbox (0, against 2–3 for either wording alone).

The planning module uses the same service for disruption messages, planner commands, rejection comments and shift notes. Its design, measurements and user guide are separate documents: Plant APS design and APS workbench guide.

7.2 Vision defects

  • Start with anomaly detection trained on good parts only (PatchCore or PaDiM family, for example from Anomalib), because defect images are rare at first. Add a supervised classifier once QA reviews have labelled enough real defects.
  • Map the anomaly score to a calibrated probability on a held-out set of good and defective images, so the 50% gate means something.
  • Store the heatmap with the image so a reviewer sees where the model looked. Target: scoring inside one station cycle (cycle time is an open question).

7.3 Predictive maintenance

  • Features per second or per cycle: RMS, peak, kurtosis, FFT band energies, spindle load, and the tool-life counter from the PLC.
  • A per-machine baseline plus a multivariate anomaly score (isolation forest or a small autoencoder) produces a health index.
  • Remaining-useful-life estimates only once real failure history exists; until then, a health trend and a warning, not a date.

  • An LLM never writes a disposition, approves a model or touches a PLC. Its only write is a draft a named person accepts.
  • LLM tools are read-only with the reviewer role; every prompt, tool call and answer is logged with the user who asked.

  • Load follows people, not units: a few summaries per line per day plus one explanation per held unit (about 4% of records in the demo run).

11Model lifecycle and feedback loop

Every QA review is a label, and every model, rule or policy change passes the same five gates before it decides anything on a line.

MetricWhy it matters
Escape rate of auto-released unitsThe number that matters most; comes from random audits (for example 1% per station) and downstream findings
False-hold rateReviewer time spent on good parts
Agreement with reviewersPlain accuracy against human decisions
Calibration errorWhether “80% confident” is right 80% of the time; the gate depends on it
Hold rate and confidence over timeEarly sign of drift: new operators, a new product, a changed camera

The gate for each model and class is the lowest confidence at which the escape rate on reviewed and audited data stays under target. It is recomputed monthly and changes only through the same approval.

Improving Laya goes through the same gates, cheapest step first, all with laya_train in the repo: reword questions and tune gates on a dev set; calibrate (the multilingual checkpoint ships with no fitted temperatures, and fitting needs a few hundred labelled answers per question type and option count); fine-tune on the plant's own labelled texts on a GPU inside the plant once a few thousand exist, then calibrate on separate records. Labels come from normal use: QA reviews, and every planner decision on a Laya reading in planning. A trained checkpoint replaces a published one only for the module it was trained for, and only after it beats it on the held-out set.

Every calibration and fine-tuning run records its data, settings, curves, before-and-after scores, temperatures and how far each part of the network moved; the platform shows them at /training/. The first demonstration run fine-tuned the multilingual checkpoint on 41 planning messages and lifted accuracy on 50 others from 63% to 78%, with calibration error from 0.22 to 0.08: too little data to deploy, but proof that the loop runs on this hardware (11 minutes on a laptop CPU).

12Security

Zones and conduits per IEC 62443: the plant floor is never reachable from outside, and every connection carries its own certificate. The demo's shared bearer key over plain HTTP is replaced in phase 1.

  • Identity: one X.509 certificate per edge node and per collector; MQTT topic ACLs let a node publish only its own line's topics. Keys in the TPM where the hardware has one.
  • Supply chain: container images, models, rules and policies are signed; edge nodes refuse anything unsigned or signed by an unknown key. In the source repository, main changes only through reviewed pull requests; no branch can be force-pushed or deleted by contributors.
  • People: single sign-on with four roles: operator, QA reviewer, quality engineer (approves models, rules and policy), administrator. Reviews, approvals and config changes go to an append-only audit log.
  • Untrusted text: notes, supplier documents and web content are data, never instructions. Anything an AI agent will act on passes Laya's prompt-injection guard first.

14Reliability and failure modes

Every failure makes the system hold more units or buffer more data; none makes it release a unit it could not check.

Plant network or hub downEdge keeps inspecting; holds reviewed on the line dashboardBridge drains; hub backfills from the 7-day store

Model service crashes or times outUnits needing it are held; others flowContainer restarts
New model misbehavesHold rate or disagreement jumps on the canary lineRollback to the version on disk, offline

Each row becomes an automated test that kills or blocks the component and checks the outcome. The demo already tests gateway buffering through an outage.

15Build plan

Backbone first, then the feedback loop, so every model added after it is measured from day one. Phases 1 to 4 run entirely on simulators; real hardware arrives in phase 5.

Predictive maintenance comes before vision because it uses sensors most machines already have; vision needs cameras, lighting, a GPU and labelled images. Phase 1 starts by moving the demo's worker, rules and policy into an inspect service that subscribes to MQTT, with its 69 tests as the regression suite.
